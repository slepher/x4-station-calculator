# station-dlc-tag 设计说明

## 设计目标
本次设计要把 `dlc-setting` 中已经定义好的 DLC 激活语义真正接入空间站规划界面。
核心目标有三点：
- 让用户在模块列表和搜索结果中直接看到模块所属 DLC 及其激活状态
- 在启用 `enforceDlcActivation` 后，统一过滤未激活 DLC 的搜索候选与计算输入
- 对已添加但未激活的模块保留可见上下文，但限制其可编辑性并明确弱化视觉状态

## 1. UI 接入设计

### 1.1 已添加模块列表
- 已添加模块列表中的模块项继续沿用现有卡片/行结构。
- DLC 标签插入在模块名称右侧，使用紧凑 `tag` 形态，不改变模块主标题的阅读顺序。
- 模块项根据 DLC 激活状态拆分为两类呈现：
  - 激活模块：保持现有亮度与交互
  - 未激活模块：整项置暗、数量控件禁用、删除按钮保留

### 1.2 搜索结果弹层
- 搜索候选弹层中的每个候选模块同样在名称右侧增加 DLC 标签。
- 当 `enforceDlcActivation = false` 时，候选列表仅展示标签状态，不做候选剔除。
- 当 `enforceDlcActivation = true` 时，候选构建阶段就排除未激活 DLC 模块。
- 分组渲染继续沿用现有“先分组、后展示”的结构，但组数据必须在 DLC 过滤后重新判断是否为空。

### 1.3 标签文案与样式
- 标签文案使用游戏数据中的 DLC `nameId`，通过游戏 i18n 翻译链解析，而不是原始 `dlc_tag` 或应用侧自定义名称表。
- 样式语义固定为：
  - 激活：绿色边框 + 绿色文字
  - 未激活：红色边框 + 红色文字
- `base` 不显示标签，避免基础内容占用额外视觉权重。

## 2. 状态来源设计

### 2.1 单一来源
- 空间站界面不直接访问 `localStorage` 或自行解析 DLC setting。
- 统一从 `useGameDataStore` 读取：
  - `activeDlcs`
  - `enforceDlcActivation`
  - `isDlcActive(dlcTag)`
  - `filterActiveDlcItems(items)`

### 2.2 UI 需要的派生信息
- 页面层需要为模块项派生：
  - `isModuleDlcActive`
  - `localizedDlcLabel`
  - `isInactiveBecauseOfDlc`
- 其中：
  - `isModuleDlcActive` 由 `isDlcActive(m.dlc_tag)` 计算
  - `isInactiveBecauseOfDlc` 由 `enforceDlcActivation && !isModuleDlcActive` 计算
- 这样可以把“标签颜色”和“禁用/置暗语义”分离，避免标签状态和交互状态耦合。

## 3. 搜索结果过滤设计

### 3.1 过滤入口
- 现有模块搜索逻辑先生成分组结果。
- 为了满足“空组不显示”，DLC 过滤应发生在模块分组生成流程内，或发生在其紧后阶段并重建空组剔除。
- 不能只在最终点击阶段阻止添加，否则：
  - 用户仍会看到未激活模块
  - 空组也无法自然消失

### 3.2 过滤规则
- 当 `enforceDlcActivation = false`：
  - 搜索逻辑返回全部命中模块
- 当 `enforceDlcActivation = true`：
  - 仅保留 `isDlcActive(m.dlc_tag) === true` 的模块
  - 分组内模块过滤后若为空数组，则整个分组不输出

### 3.3 展示一致性
- 搜索结果中的标签状态始终展示，即使当前开启了过滤。
- 这意味着：
  - 激活模块标签仍然可见
  - 被过滤掉的未激活模块不会残留占位或空白分割线

## 4. 已添加模块禁用态设计

### 4.1 保留显示，不参与编辑
- 已添加但未激活的模块不能直接隐藏。
- 保留显示可以让用户继续看到历史配置和问题来源。
- 该类模块项需要：
  - 整项降低对比度或透明度
  - 数量编辑控件进入禁用态
  - 删除按钮保持可用

### 4.2 交互边界
- “不可更改数量”仅限制数量相关操作。
- 删除动作保留，以便用户自行清理未激活模块。
- 不在本次 change 中新增专门的迁移提示、修复向导或批量删除交互。

## 5. 计算过滤设计

### 5.1 过滤目标
- 当 `enforceDlcActivation = true` 时，未激活 DLC 模块不得进入空间站计算输入。
- 过滤不应只落在某一个展示结果层，而应落在模块分析链路的统一入口或共享数据源上。
- 这样才能保证以下结果都同步收敛：
  - 产出/消耗
  - 建造成本
  - 工人需求
  - 仓储与体积
  - Ware flow / station analysis 等派生分析

### 5.2 关闭策略时的兼容行为
- 当 `enforceDlcActivation = false` 时，不做计算过滤。
- 这样可以保持 setting 文档中“关闭策略时不强制隐藏或禁算”的既有语义。

### 5.3 统一输入原则
- 计算过滤应复用 `useGameDataStore` 的 DLC helper，不额外发明第二套判断逻辑。
- 若存在多个计算入口，应在尽可能靠前的模块列表输入阶段完成过滤，避免不同分析函数各自实现一遍 DLC 排除。
- DLC 设置变化后需要触发空间站重算，保证：
  - 自动工业区会基于新的激活 DLC 集合重新补全
  - 既有分析结果不会保留旧 DLC 状态下的缓存

## 6. 风险与对策

- 风险：只在 UI 上置暗已添加模块，但底层分析仍继续把它们纳入计算。
  - 对策：在共享计算输入阶段统一过滤未激活 DLC 模块，而不是只做表现层禁用。
- 风险：只在搜索结果渲染后隐藏节点，导致分组 header 残留空壳。
  - 对策：在分组数据生成阶段或分组后立即执行空组剔除。
- 风险：标签状态和可编辑状态混在一起，导致 `enforceDlcActivation = false` 时也误禁用模块。
  - 对策：将“DLC 是否激活”和“当前是否因策略开启而禁用”拆成两个独立派生状态。
- 风险：页面再次直接读取存储，造成与 `dlc-setting` 的语义漂移。
  - 对策：强制通过 `useGameDataStore` 作为唯一 DLC 状态来源。
- 风险：`base` 被误判为未激活，导致基础模块出现错误红标或被过滤。
  - 对策：继续遵循 `isDlcActive('base') === true` 的统一规则，但展示层不渲染 `base` 标签。
- 风险：DLC 设置变化后未触发空间站重算，导致自动工业区或分析结果残留旧状态。
  - 对策：将 `activeDlcs` 与 `enforceDlcActivation` 纳入空间站重算依赖。
