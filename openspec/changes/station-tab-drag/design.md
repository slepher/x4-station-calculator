## Context

当前 `StationTabBar` 仅支持点击切换，不支持拖拽排序。项目已引入 `vuedraggable`，并存在拖拽相关 E2E 测试基础设施，因此本次可以在不引入新依赖的前提下实现标签重排。约束点是“帝国总览”标签必须固定首位且不参与排序，同时重排结果需要写回 EmpireStore 并持久化，避免刷新后顺序丢失。

## Goals / Non-Goals

**Goals:**
- 为空间站标签提供稳定的拖拽重排交互。
- 保持“帝国总览”标签固定在最左侧。
- 拖拽结束后同步更新 store 与存储，使顺序可恢复。
- 保证当前激活分站在重排后仍保持激活。

**Non-Goals:**
- 不改变空间站创建/删除/复制业务规则。
- 不改动帝国总览与分站内容区域布局。
- 不引入跨帝国拖拽或跨页面拖拽能力。

## Decisions

1. 使用现有 `vuedraggable` 封装动态分站标签区域，不把“帝国总览”放入可拖拽列表。
- 备选方案 A：手写 Pointer 事件与命中判断。缺点是复杂度高、维护成本高。
- 备选方案 B：仅键盘上移/下移按钮。缺点是效率与直觉性不足。
- 选择理由：复用现有依赖与测试经验，最小实现成本。

2. 在 EmpireStore 提供显式 `reorderStations(fromIndex, toIndex)`（或等价动作）统一处理顺序变更。
- 备选方案：组件层直接改数组。缺点是状态变更路径分散，不利于持久化与测试。
- 选择理由：集中状态更新逻辑，便于单元测试和未来审计。

3. 持久化策略沿用现有帝国保存机制：重排后标记为变更态，保存时写入 `stations` 新顺序。
- 备选方案：每次拖拽立刻写 localStorage。缺点是频繁写入、与现有“显式保存”语义不一致。
- 选择理由：与当前数据流一致，减少行为分歧。

4. 拖拽可视反馈采用“拖拽项半透明 + 目标占位高亮”最小规范。
- 备选方案：复杂动画/阴影跟随。缺点是实现与测试成本升高。
- 选择理由：优先保证可用性与可测性。

5. E2E 拖拽执行策略固定为 `mouse.move`，单次拖动操作等待约 2 秒，失败最多重试 2 次。
- 备选方案：`dragTo` 或直接派发 `DragEvent`。缺点是与当前组件实现耦合较强，稳定性波动更大。
- 选择理由：与现有 Playwright Mouse API 经验一致，可更稳定复现用户操作轨迹。

## Risks / Trade-offs

- [Risk] 拖拽触发点击，导致错误切换标签 → Mitigation: 在 drag start/end 阶段屏蔽点击或使用最小拖拽阈值。
- [Risk] 索引映射错误（固定总览标签 + 动态标签）→ Mitigation: 拖拽列表仅包含 stations，索引直接对应 `stations[]`。
- [Risk] 重排后激活态丢失 → Mitigation: 以 `activeStationId` 为真源，重排仅变更数组顺序不改 ID。
- [Risk] E2E 在不同浏览器拖拽不稳定 → Mitigation: 采用已有 Mouse API 拖拽模式与稳定定位器。

## Migration Plan

- 该变更无数据结构迁移。
- 对已有存档仅改变 `stations` 数组顺序语义，旧数据可直接读取。
- 若回滚实现，数据仍可按数组顺序展示，不影响可读性。
