# 设计说明：import-logic-flow

## 1. 目标

在不改变现有存档体系的前提下，新增“逻辑组网导入到站点/帝国”的可执行流程，并保证：

1. 用户在导入前可明确确认动作。
2. 导入映射可追踪、可解释。
3. 跳过项/忽略项有统一 warning 汇总反馈。
4. 默认组名逻辑跨 UI 复用，修正 store 自动写入默认名的行为偏差。

## 2. 范围

### 2.1 包含

1. 导入入口 UI 调整（空间站与帝国总览）。
2. 逻辑组网方案/规划区选择弹窗。
3. 导入确认流程（Empire 复用 SmartSaveDialog；Station 使用独立导入确认弹窗）。
4. 导入映射实现（`manual` -> `plannedModules`，`isolated` 资源锁定）。
5. warning 汇总弹窗。
6. 默认组名算法抽取为通用函数。

### 2.2 不包含

1. 导入后自动保存。
2. 逻辑组网拖拽与编辑行为重构。
3. 非导入路径的业务改造。

## 3. 总体架构

### 3.1 导入流程分层

1. **UI 触发层**：入口按钮、选择弹窗、确认弹窗。
2. **导入编排层**：根据上下文（Empire/Station）组织目标对象、执行映射、收集 warning。
3. **映射层（纯函数优先）**：把 `SavedFlowGroup` 转换为 `plannedModules` 与 `isolated` 锁定集合。
4. **状态写入层**：调用 store 接口一次性写入目标站点状态。
5. **反馈层**：统一 warning 汇总弹窗。

### 3.2 核心数据约定

输入来自逻辑组网持久化结构：

1. `LogicFlowPlan.groups[].nodes[]`
2. 使用 `source === 'manual'` 参与模块映射。
3. 使用 `isIsolated === true` 参与锁定候选收集。

## 4. 关键设计决策

### 4.1 Empire 导入确认

1. 复用 `SmartSaveDialog`，但按条件触发（非总是弹出）。
2. 文案语义映射为“保存并导入 / 放弃并导入”。
3. 不改变 SmartSaveDialog 既有保存机制，只在确认后接入导入执行。
4. 触发条件与“新建按钮”判定逻辑逐条一致。
5. 判定逻辑统一复用，不在导入路径重复实现。

### 4.2 Station 导入确认

1. 使用独立导入确认弹窗（避免与 `NEW/SAVE_AS` 语义耦合）。
2. 提供两种执行分支：
   - 导入为新空间站。
   - 覆盖当前空间站（先清空再导入）。

### 4.3 导入选择界面约束（本轮补充）

1. 帝国导入：切换为“加载帝国”界面形态；实现上直接改造当前导入模板，不新增并行模板，且不提供删除入口。
2. 空间站导入：一级保持下拉；二级在选中方案后以“加载帝国”同风格展示规划区内容。
3. 空间站二级内容区仅展示可导入规划区，自动隐藏空规划区。
4. 空间站二级内容区按规划区提供“直接导入”按钮，不使用先选中后统一继续的交互。
5. 若方案下无可导入规划区，展示空态文案“该方案下暂无可导入的规划区”。
6. 帝国方案卡片与空间站规划区卡片均保留详情预览（更新时间、统计摘要、预览条目、`+N more...`）。
7. 导入触发统一收敛为卡片内直接动作；移除底部“继续”按钮触发路径。
8. 二级内容区不新增搜索、分页、排序能力。
9. 以上仅调整界面呈现，不引入新的导入业务逻辑。

### 4.4 保存确认判定复用（本轮补充）

1. “导入是否弹保存确认框”与“新建是否弹保存确认框”共享同一判定逻辑。
2. 若判定逻辑在组件层，需上提至 store 统一管理。
3. 导入路径仅消费判定结果：
   - 需要确认：弹 `SmartSaveDialog`。
   - 不需要确认：直接执行导入。
4. dirty 判定仅基于帝国业务数据（名称、站点集合、模块/设置等）变化。
5. `activeStationId` 属于视图上下文，不计入 dirty 判定。
   - 例如：站点页切到帝国总览（`activeStationId` 变为 `null`）不得单独触发“需要保存确认”。

### 4.5 映射规则

1. `manual` 节点：
   - 通过 `node.moduleId` 统计到 `plannedModules`。
   - 同模块按数量聚合。
2. `isolated` 资源：
   - 仅当 ware.transport 为 `container` 时写入锁定集合。
   - 非 `container` 不写入，记录 warning。
3. Empire 全量方案导入：
   - 每个“非空规划区”创建一站。
   - 空规划区（无 `manual`）跳过并记录 warning。

### 4.6 warning 汇总机制

导入编排层维护 `warnings[]`：

1. 空规划区跳过。
2. 非 `container` 的 `isolated` 被忽略。
3. 其他可预期降级行为（如无效节点）可扩展进入同一集合。

执行完成后：

1. 若 `warnings.length > 0`，统一弹出单个汇总弹窗。
2. 若无 warning，不弹汇总。

### 4.7 默认组名通用逻辑

抽取通用函数（建议 `src/store/logic/logicFlowGroupName.ts`）：

1. 输入：group 节点集合 + wares 显示访问能力。
2. 规则：
   - 仅在 `group.name` 为空时计算。
   - 取最高 tier 的 `manual` 节点。
   - 同 tier 优先非 isolated，再按 order。
3. 输出：展示名字符串。

应用位置：

1. `ProductionLineGroup.vue`
2. `LogicFlowPlanningZone.vue`
3. `LoadFlowPlanModal.vue`

并移除 store 自动写回默认名路径，保证默认名只作为显示派生值。

## 5. 风险与缓解

1. **风险**：导入流程分支多，容易遗漏 warning 展示。
   - **缓解**：导入编排统一返回 `{ result, warnings }`，UI 仅消费一个出口。
2. **风险**：Empire 导入批量建站可能影响当前 active station 选中态。
   - **缓解**：明确导入后选中策略（保持当前或切换最后创建），并在实现中固定。
3. **风险**：默认组名函数抽取后可能与旧显示细节不一致。
   - **缓解**：对三处 UI 做对齐测试，确保相同输入返回一致输出。

## 6. 与既有行为兼容性

1. 保持“导入后不自动保存”。
2. 保持现有 `container` 锁定能力边界。
3. 不改动普通 XML/GameCom 导入路径。
4. 站点/总览切换不再引发额外 dirty；保存确认触发信号更聚焦于业务数据变更。
