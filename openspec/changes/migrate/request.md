# migrate：Python processor 迁移到 TypeScript

## 目标

将生成 X4 游戏数据的 Python processor 及其运行时依赖迁移到 TypeScript，统一 npm/CLI 执行入口、参数、进度和错误提示。完成后，范围内的数据、地图和资源任务无需 Python，现有前端消费的 JSON 保持兼容。

## 已确认方案（审核重点）

### 执行入口

- “执行界面统一”按本次计划落实为命令行统一，不新增网页界面。
- 使用 `npm run process -- <data|map|resources> [options]`，由一个 TS 入口分派任务，使用现有 `tsx` 执行。
- `data` 保持基础数据流水线包含地图处理的行为；`map` 可独立执行；`resources` 显式执行，不因运行 `data` 自动启动昂贵资源计算。
- 三个任务统一读取 `x4-station-calculator.config.json`。无版本参数时使用配置中的当前版本及 beta 状态；指定版本存在多个候选时必须显式选择 beta/stable；版本选择和 flavor 选项分别互斥；全版本按配置顺序串行运行。
- 将资源入口旧有固定默认 8.0 改为统一的配置默认版本，并在帮助和迁移说明中明确这一行为变化。
- 保留单星区更新、强制逐格重算、资源输入路径和存档目录选项。地图旧入口中声明但未传入服务的路径参数，迁移时实现显式覆盖，并逐项验证；不继续接受参数却忽略其值。
- 提供帮助、版本与阶段进度、输出摘要；无效参数、版本不存在、缺少必要输入及处理失败返回非零退出码，不报告成功或静默切换到其他输入。
- 全版本首个失败停止后续版本。`--all-versions` 按配置处理所有版本项，不以 flavor 隐式过滤。
- 提供 `--output-dir` 隔离输出根目录，保留 `data/`、`locales/` 布局；已支持的单文件覆盖优先。资源未指定该目录时继续由 `maps-json` 所在目录确定输出。

### 迁移范围与顺序

- 先明确实际调用链和输入输出契约，再建立隔离输出对照，依次迁移共享能力、地图、基础数据及资源计算。
- 基础数据包含商品、配方、工人消耗、模块、飞船、装备、导弹、弹丸、无人机、消耗品、语言、分类和资源元数据，以及主入口调用的 factions、terraforming、research、blueprints。
- 地图与资源覆盖现有 8.0 `regions` 和 9.0+ `resourceareas` 分支；不扩展到现有实现不支持的资源模型。
- 保留现有名称解析、DLC 覆盖顺序、业务修正、字段、数组顺序及运行阶段依赖。每次运行独立持有配置、索引与语言状态，多版本之间不得串数据。
- 复用已安装的 XML/CLI/TS 工具和适用的已有类型，不机械复制历史重复模块，不新增通用插件框架或额外 UI 中间层。

### 输出、缓存与数值

- 保持既有产物清单、目录布局与数据语义。`maps.json` 保持纯地图结构，资源任务不得修改它；资源结果写入 `map_resources.json` 及既有资源明细/缓存产物。
- 对照运行使用相同原始输入、存档输入和缓存初始状态，Python 与 TS 输出和缓存分别隔离，不覆盖正式资产。
- 保留缓存命中、缺失星区补算、单星区合并及强制重算的分支规则。增量更新不得丢失其他星区。
- 实施确认旧 Python 单星区输出会覆盖其他星区摘要（bugs.md B001）；TS 按上述保留要求修正，目标星区精确对照 Python，非目标星区精确对照执行前副本，不复刻该数据丢失行为。
- 逐格缓存默认按 `analysis/resources/<folder_name>/resourcearea_blocks.json` 隔离，支持 `--blocks-cache` 覆盖；旧无版本缓存保留但不自动复用。缺失按冷缓存处理，损坏报错，可显式强制重算恢复。先计算/合并完成再替换文件，计算失败不得覆盖原缓存及资源产物。
- 模型不支持的选项若显式传入应报错。默认存档目录缺失保留无存档计算行为，显式指定不存在的目录报错。
- 严格验证舍入、负数截断、float32 中间步骤、位运算、噪声及边界采样语义，不直接用 JavaScript 默认运算替代 Python 的不同语义。
- JSON 比较忽略对象 key 顺序和格式差异，但保留数组顺序、字段缺失/null、值及类型差异。整数结果要求一致；浮点差异必须定位来源，只有明确证明不可避免并经确认的字段才可设置局部容差，不使用全局容差掩盖偏差。

### 切换与清理

- 迁移过程中 Python 仅作为对照基线；若临时由 TS 调用 Python，必须明确标注未迁移，不能计作完成。
- 切换实际调用文档和命令后验证完整 TS 链路；用户验证通过后再移除已替代的 Python 入口、实现及其专属依赖。保留范围外脚本仍然使用的共享代码。
- 编写与实现任务绑定的必要 Unit 回归测试，并执行类型检查和 `npm run build`；不重建未修改的 Rust parser。

## 边界

### In Scope

- 三个 TS 任务、共享配置/解析/输出能力，以及它们实际依赖的 Python 业务实现。
- 有实际调用方的历史 processor 入口，包括 `x4_data_map_processor.py`，需先核对使用情况，再迁移调用方到对应任务；无需复制其未使用的重复实现。
- 对照工具、必要样例与 Unit 覆盖、执行文档更新和用户验收后的 Python 清理。

### Out of Scope

- 新增网页运行面板、前端 store/presenter/Vue 重构、改变游戏数据 schema 或重新设计资源算法。
- 资产解包/蒸馏、worktree server、临时分析、独立研究/replay 脚本；只有 processor 实际调用的代码才进入迁移依赖闭包。
- 新游戏版本支持、无实测依据的并行化/worker/缓存框架、新增依赖及 Rust/WASM 重建。
- 本文档阶段的代码实现、正式资产生成、提交或归档。

## 验收标准（DoD）

1. 三个 npm 任务均有可用帮助及一致的参数/日志/退出规则，最终运行链路没有 Python 调用。
2. 默认版本、显式版本、beta/stable、多候选错误和全版本串行执行通过测试；同进程连续处理版本不会污染状态。
3. 基础数据全部产物与同输入 Python 对照一致，包括主入口依赖的四个扩展业务。
4. 8.0 与配置中的 9.0+ 地图/资源模型通过代表性对照；资源执行前后 `maps.json` 字节内容不变。
5. 冷缓存、热缓存、缺失星区补算、单星区更新、强制重算与存档参与计算均符合原业务规则，保留非目标星区；版本之间不得误用缓存。
6. 对照报告覆盖文件缺失/多出、结构、字段和数值差异，未解释差异为零；记录完整运行耗时与峰值内存，不设置未经测量的性能目标。
7. 相关 Unit 测试、TS 类型检查及 `npm run build` 通过；文档指向统一入口。
8. 用户验证通过后清理被替代的 Python 实现，范围外脚本及其依赖仍可使用。

## 未决项

无。实际调用方、产物清单与基线输入可用性在实施首项调查中记录；若原始数据不齐，必须报告对应版本无法完成全量验收，不能以现有 JSON 代替同输入 Python 基线。
