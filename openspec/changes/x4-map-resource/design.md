# x4-map-resource 设计说明

## 设计目标
在不破坏现有 map 搜索交互的前提下，为 `MapWorkbenchView` 增加一套右上角资源筛选工作台。
该工作台需要同时解决三个问题：
- 资源多选与每项独立最低丰度配置
- 命中候选的稳定排序与快速聚焦
- 搜索命中和资源命中的高亮分层

## 1. UI 设计

### 1.1 右上常驻资源面板
- 在 `MapWorkbenchView` 右上角增加一个绝对定位面板，与左上搜索框形成对称布局。
- 面板保持常驻，不提供折叠或关闭按钮。
- 面板结构分为三段：
  - 资源 tag 区：负责选择参与筛选的资源
  - 配置区：负责已选资源的最低丰度设置
  - 命中候选框：负责展示满足条件的 sector

### 1.2 配置区的层次
- 每个已选资源单独渲染一行，左侧显示资源名或小 tag，右侧显示最低丰度下拉。
- 当已选资源数量大于 `2` 时，在配置区顶部增加 `所有项` 行。
- `所有项` 是批量操作入口，只对当前已选资源生效，不改变未选中资源的默认值。
- 不将下拉嵌入资源 tag 内部，避免 tag 宽度突变、换行不稳定和误触。

### 1.3 命中候选框
- 命中候选框位于配置区下方，只在至少选择一个资源时显示。
- 列表最多显示 `10` 个 sector。
- 每个候选项至少显示 sector 主名称；可附加总分或资源摘要，但不作为本次必需行为。
- 点击候选项后，复用现有搜索候选的聚焦与选中逻辑。

## 2. 数据与状态设计

### 2.1 资源配置状态
- 资源筛选状态建议使用按资源键控的结构：
  - 是否选中
  - 当前最低丰度
- 这样可以让每个资源独立维护门槛，并支持批量更新时只改写已选项。

### 2.2 丰度等级索引
- 基于 `regionyields.json` 为每个资源构建一份 `yield name -> rank` 的顺序索引。
- 比较最低丰度时，不直接比较字符串，而是比较 rank。
- 即便当前多个资源的等级名称集合一致，仍按“每个资源独立建立索引”实现，避免把数据结构假设写死。

### 2.3 sector 资源命中计算
- 命中判定使用 `maps.json` 中 sector 的 `resources[]`。
- 对每个已选资源执行：
  - sector 中必须存在该资源
  - sector 该资源的 `yield` rank 必须大于等于最低丰度 rank
- 只有全部已选资源都通过时，sector 才进入命中集合。

### 2.4 命中排序分数
- 候选排序分数定义为：当前已选资源在该 sector 中的 `level` 之和。
- 分数仅用于排序，不用于最低丰度判定。
- 同分时建议以显示名或 sector id 做稳定次序，避免列表跳动。

## 3. 搜索与资源筛选并存设计

### 3.1 双通道结果集
- 搜索结果与资源筛选结果分别计算，不互相裁剪。
- 左上搜索继续负责：
  - 名称匹配
  - 搜索候选
  - 搜索聚焦
- 右上资源面板负责：
  - 资源条件配置
  - 资源候选列表
  - 资源命中高亮

### 3.2 渲染优先级
- 地图渲染层不要只维护单一 `highlightedSectorIds`。
- 建议拆成三类输入：
  - `selectedSectorId`
  - `searchHighlightedSectorIds`
  - `resourceHighlightedSectorIds`
- 样式优先级固定为：
  - 选中态
  - 搜索高亮
  - 资源高亮

### 3.3 交互一致性
- 资源候选点击应直接复用搜索候选的 focus 逻辑，避免产生两套不同的地图聚焦行为。
- 点击资源候选后，不清空资源筛选条件，也不自动修改搜索输入。
- 搜索清空只清理搜索态；资源清空只清理资源筛选态，两者互不越界。

## 4. 风险与对策

- 风险：右上面板内容增长后遮挡地图过多。
  - 对策：控制面板宽度、候选上限和配置区只渲染已选资源。
- 风险：同时存在搜索命中和资源命中时，用户难以理解高亮来源。
  - 对策：固定优先级，并在视觉上让资源高亮弱于搜索高亮。
- 风险：批量修改 `所有项` 时覆盖用户逐项配置，造成误判。
  - 对策：将 `所有项` 明确设计成一次性同步操作，且只在已选资源超过 `2` 个时出现。
- 风险：使用 `yield` 判门槛、使用 `level` 排序，逻辑来源不同易混淆。
  - 对策：在实现中明确拆分“通过条件”和“排序分数”两个计算阶段。
