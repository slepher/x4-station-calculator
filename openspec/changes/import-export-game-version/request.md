# import-export-game-version 需求说明

## 目标
增强现有导入/导出能力，使导出文件显式携带当前游戏版本信息，并在导入时对版本差异与跨版本失效数据给出可见提示。
同时统一导入/导出模块名称的 i18n 语义，使其与版本切换场景保持一致，并彻底将面向用户的 `Empire / 帝国` 文案收敛为 `Sector / 星区`。

## 已确认方案（审核重点）

### 1. 导出文件携带游戏版本元数据
- 导出 JSON 顶层在现有 `format / version / exportedAt / data` 之外，新增：
  - `game_vsn`
  - `beta`
- `game_vsn` 与 `beta` 来自当前生效的游戏版本选择，即 `useGameDataStore.currentVersion` 与 `useGameDataStore.isBeta`。
- 导出数据本身继续来自当前版本作用域下的三个 store 状态：
  - `savedEmpires`
  - `savedPlans`
  - `savedBlueprints`
- 这些 store 已通过版本切换后的 `storage key` 读取对应版本的数据，因此导出源数据天然跟随当前版本，不需要额外引入独立 storage-key 选择逻辑。
- 这些字段属于导出文件协议的一部分，供导入阶段直接消费。

### 2. 导出弹窗显示当前游戏版本
- 导出弹窗除现有文件名输入框与模块统计外，还要显示“当前游戏版本”。
- 显示内容至少包含：
  - 当前版本号
  - 当前是否为 beta
- 该版本信息必须是用户可见的 UI，而不是仅写入 JSON。

### 3. 导出默认文件名包含版本与 beta 后缀
- 导出默认文件名要带上当前 `game_vsn`。
- 若当前版本为 beta，则文件名额外带 `beta` 后缀。
- 若用户手工修改文件名，系统仍保持现有规则：缺失 `.json` 时自动补后缀。

### 4. 导入时显示文件版本与当前版本差异
- 文件上传解析成功后，系统读取导入文件中的 `game_vsn` 与 `beta`。
- 若导入文件的 `game_vsn` 或 `beta` 与当前应用版本不一致，导入界面必须额外显示差异提示。
- 该提示属于警告信息，不直接阻止导入。
- 若文件缺少这两个字段，则按旧协议处理，默认解释为：
  - `game_vsn = 8.0`
  - `beta = false`
- 在这种情况下，后续版本差异比较也以 `8.0 stable` 为文件版本来源。

### 5. 导入前对三个存储模块做失效数据检查
- 文件在完成 JSON 解析后、正式应用导入前，要对三个模块执行额外校验：
  - `x4_empire_data`
  - `x4_logic_flow_plans`
  - `x4_ship_blueprints`
- 校验依据是“当前游戏版本下真实存在的数据”，而不是导入文件自身版本。
- 发现引用对象在当前游戏数据中不存在时，系统要在导入前完成安全清洗，并产出面向用户的汇总提示。

### 6. Empire 模块的失效清洗规则
- 校验站点中的 `modules[].id`。
- 若模块在当前游戏版本中不存在，则从该站点模块列表中移除该条目。
- 该清洗属于导入预处理的一部分，不要求保留空壳占位。

### 7. Logic Flow 模块的失效清洗规则
- 校验 flow 节点中的模块引用（`node.module`）。
- 若该模块在当前游戏版本中不存在，则从对应 group 中移除该无效节点。
- `isolated` ware 节点不纳入本次模块存在性检查。

### 8. Ship Blueprint 模块的失效清洗规则
- 校验至少包括以下引用：
  - `shipId`
  - `connections[].group[].equipment_id`
  - `connections[].group[].shield.equipment_id`
  - `storage.deployables[].id`
  - `storage.countermeasure.id`
  - `storage.drones[].id`
  - `storage.missiles[].id`
- 校验发现不存在时，按结构安全清洗：
  - 无效 `shipId` 对应的整条 blueprint 移除
  - 无效装备引用置空或移除对应 group 内容
  - 无效仓储物品从列表中移除，或将单值槽位清空
- 这里的“置空”不是机械写入 `null`，而是按当前数据结构执行可安全回灌的清空动作。

### 9. 导入界面展示逐模块清洗说明
- 解析完成后，导入界面需要展示每个模块的清洗摘要。
- 摘要按模块维度聚合，而不是只给全局一条 warning。
- 摘要文本应表达“有多少模块/装备/舰船/仓储物品不存在，已从存档中移除”。
- 这些摘要在执行导入后也应能作为 warning 汇总进入状态消息。

### 10. 导入/导出模块名称 i18n 统一
- 导入/导出弹窗中的模块名称，要与版本切换场景的模块命名语义对齐。
- 不允许继续保留一套与版本切换平行、容易漂移的独立命名。
- 面向用户的三类模块名称需要统一为同一套语义来源。

### 11. Empire 命名统一替换为 Sector
- 若导入/导出、版本切换或相关提示中仍存在将该模块命名为 `Empire / 帝国` 的用户可见文案，本次统一改为 `Sector / 星区`。
- 这不仅包括翻译 value，也包括相关 i18n key 命名应同步调整，避免 key 语义继续保留旧概念。
- 目标是从命名层消除“内部结构叫 empire、用户文案叫 sector”造成的混乱。

## 边界

### In Scope
- 导出 payload 增加 `game_vsn` 与 `beta`。
- 导出弹窗新增当前游戏版本显示与默认文件名版本后缀。
- 导入弹窗新增版本差异提示与逐模块清洗摘要。
- 导入前对 `x4_empire_data`、`x4_logic_flow_plans`、`x4_ship_blueprints` 执行失效引用清洗。
- 统一导入/导出与版本切换相关模块名称的 i18n 语义。
- 将用户可见的 `Empire / 帝国` 模块命名统一替换为 `Sector / 星区`。

### Out of Scope
- 不改变现有导入模式（覆盖 / 增量）的基础行为。
- 不引入跨版本自动迁移策略以保留失效对象。
- 不扩展到 ware、地图资源等非本次明确要求的额外实体校验。
- 不修改与导入/导出无关的业务计算口径。

## 验收标准（DoD）
1. 导出文件顶层包含 `game_vsn` 与 `beta` 字段，并保持现有 `data` 结构不变。
2. 导出弹窗可见显示当前游戏版本信息。
3. 导出默认文件名包含版本号；beta 版本额外包含 `beta` 后缀。
4. 导入文件解析后，若文件版本与当前版本不一致，界面会显示明确差异提示。
5. 缺失版本元数据的旧 JSON 文件会被默认解释为 `8.0 stable`。
6. 导入前会基于当前游戏版本校验并清洗 `x4_empire_data`、`x4_logic_flow_plans`、`x4_ship_blueprints` 中的失效引用。
7. Empire 模块中的失效站点模块不会被导入到当前存档。
8. Logic Flow 模块中的失效模块节点不会被导入到当前存档。
9. Ship Blueprint 模块中的失效舰船、装备与仓储物品会按结构安全清洗，不留下脏引用。
10. 导入界面会按模块展示清洗摘要，并指出对应数量已从存档中移除。
11. 导入/导出模块名称的 i18n 语义与版本切换保持一致。
12. 用户可见的相关模块名称中不再出现 `Empire / 帝国`，统一为 `Sector / 星区`。
